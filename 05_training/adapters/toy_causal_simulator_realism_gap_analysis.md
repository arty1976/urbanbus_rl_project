# Toy Causal Simulator Realism Gap Analysis

## Purpose

This document analyzes the realism gap between the current Phase 2 toy causal simulator and real Daegu public bus operations.

It is intended to guide the transition from:

```text
toy causal smoke validation
```

to:

```text
causal simulator v2 design
```

This document is not a performance report.

It is a model-risk and simulator-design document.

## Current Toy Simulator Role

The current toy simulator is useful for structural validation:

```text
action affects next state
reward_v1 receives 12-KPI metrics
MAPPO-style smoke training can execute
checkpoint and evaluation pipeline can run
A-family matrix smoke evaluation can complete
```

However, it is not yet a realistic operational simulator.

## High-Level Realism Gap Summary

| Area | Current Toy Simulator | Real Bus Operation Need | Gap Severity |
|---|---|---|---|
| Network scale | Small toy graph | Full Daegu network or calibrated subnetwork | High |
| Route structure | Simplified graph movement | Route-specific stop sequences and trips | High |
| Demand | Simplified deterministic demand | Time-varying, stop/route/OD demand | High |
| Passenger queue | Aggregate proxy | Stop-level arrival, boarding, alighting, transfer | High |
| Bus movement | Simplified progression/headway | Link travel time, dwell time, traffic delay | High |
| Actions | Hold/dispatch/skip toy effects | Operationally feasible control actions | Medium-High |
| Capacity | Usually simplified | Vehicle capacity and crowding | High |
| Timetable | Simplified | Scheduled headway, dispatch table, recovery time | High |
| Traffic | Not calibrated | Road congestion and signal delay | High |
| Calibration | Not calibrated | Historical AVL/BIS validation | High |
| Validation | Smoke tests | Out-of-sample validation against real data | High |

## Gap 1 ??Network Scale and Topology

### Current State

The toy simulator uses a small graph skeleton suitable for smoke tests.

### Real Requirement

A realistic simulator needs at least a calibrated corridor or district-level network before attempting full Daegu-wide simulation.

Minimum v2 target:

```text
Suseong-gu core corridor
Beomeo-Manchon focus area
5~10 bus agents initially
route-specific stop order
direction-aware edges
```

### Risk

If the graph does not match real route topology, headway and passenger wait metrics can be structurally misleading.

### Recommendation

Causal simulator v2 should introduce:

```text
route_id
trip_id
direction_id
ordered stop sequence
link travel time distribution
```

## Gap 2 ??Demand Generation

### Current State

Demand is generated by a simplified deterministic or proxy process.

### Real Requirement

Passenger demand should vary by:

```text
stop
route
time band
weekday/weekend
school/work commute pattern
weather or event condition if available
```

### Risk

A policy can appear good in a toy simulator by serving simplified demand that does not resemble real passenger arrivals.

### Recommendation

Causal simulator v2 should support:

```text
arrival_rate_by_stop_time_band
seeded stochastic passenger arrivals
optional OD matrix
calibrated demand scaling
```

## Gap 3 ??Passenger Queue and Service Process

### Current State

Passenger queues are represented as simplified aggregate quantities.

### Real Requirement

A realistic simulator should track at least:

```text
waiting passengers by stop
served passengers
unserved passengers
passenger waiting time distribution
boarding and alighting counts
```

### Risk

Average wait and p95 wait can be inaccurate if individual passenger waiting time is not tracked.

### Recommendation

v2 should store per-stop passenger queue states and approximate passenger age buckets:

```text
queue_count
wait_age_bucket_0_5min
wait_age_bucket_5_10min
wait_age_bucket_10_20min
wait_age_bucket_20plus
```

This allows p95 wait to be computed from a more meaningful distribution.

## Gap 4 ??Bus Movement Dynamics

### Current State

Bus movement is simplified enough to verify that action changes next state.

### Real Requirement

Bus dynamics should include:

```text
link travel time
dwell time
boarding time
alighting time
traffic delay
holding delay
terminal layover
```

### Risk

If movement dynamics are too simple, the policy may exploit unrealistic transitions.

### Recommendation

v2 should use:

```text
base_link_travel_time
time_band_multiplier
stochastic_noise
dwell_time = base + boarding_count * boarding_sec + alighting_count * alighting_sec
```

## Gap 5 ??Action Feasibility

### Current State

Actions are simplified:

```text
hold
dispatch
skip
```

### Real Requirement

Real actions must respect operational constraints:

```text
maximum hold time
minimum headway
driver schedule
terminal dispatch availability
skip-stop legality
passenger service obligations
```

### Risk

A policy may learn actions that are not deployable.

### Recommendation

v2 should define an action legality layer:

```text
action_mask
illegal_action_penalty
fallback action
reason code
```

## Gap 6 ??Capacity and Crowding

### Current State

Capacity is either absent or simplified.

### Real Requirement

A real bus cannot board unlimited passengers.

### Risk

Passenger service rate can be overestimated if capacity constraints are ignored.

### Recommendation

v2 should include:

```text
vehicle_capacity
current_load
boarding_limit
left_behind_passengers
crowding_penalty
```

## Gap 7 ??Timetable and Dispatch Schedule

### Current State

The toy simulator does not fully represent scheduled dispatch and recovery.

### Real Requirement

Bus operation is constrained by:

```text
planned departure time
headway target
terminal recovery time
vehicle rotation
driver duty schedule
```

### Risk

The simulator may reward fleet reduction actions that would break real schedules.

### Recommendation

v2 should include:

```text
scheduled_trip_table
target_headway_by_time_band
terminal_recovery_buffer
vehicle_cycle_time
```

## Gap 8 ??Traffic and Signal Delay

### Current State

Traffic is simplified or absent.

### Real Requirement

Travel time varies by road segment and time period.

### Risk

A policy evaluated under fixed travel time may fail under peak congestion.

### Recommendation

v2 should add:

```text
link_time_distribution_by_time_band
congestion_multiplier
incident_delay_optional
signal_delay_proxy
```

## Gap 9 ??Calibration and Validation

### Current State

The current simulator is not calibrated against real historical outcomes.

### Real Requirement

A causal simulator must be compared against observed data:

```text
headway distribution
arrival regularity
waiting time proxy
boarding/alighting totals
route travel time
vehicle cycle time
```

### Risk

Without calibration, a causal simulator can be internally consistent but externally wrong.

### Recommendation

Before paper-level claims, v2 must pass:

```text
calibration split
validation split
out-of-sample route/time-band check
metric tolerance report
```

## Gap 10 ??Reward-Hacking Risk

### Current State

reward_v1 is guarded, but the simulator is still simplified.

### Real Requirement

The simulator must make undesirable shortcuts visible.

Examples:

```text
reducing fleet while leaving passengers behind
lowering energy by not serving demand
improving headway by skipping too many stops
lowering intervention rate by doing nothing
```

### Recommendation

v2 should preserve hard constraints:

```text
minimum passenger_service_rate
maximum p95 wait
minimum on_time_rate
maximum bunching_rate
left-behind passenger penalty
illegal action penalty
```

### State

```text

headway update

capacity update
```

### Output

```text

canonical KPI compatible outputs
calibration diagnostics
```
